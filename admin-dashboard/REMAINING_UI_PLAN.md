# خطة استكمال لوحة تحكم الإدارة

## 1. الوضع الحالي

تم بناء واجهات أولية تغطي معظم وحدات الـLaravel API، وتشمل:

- الرئيسية ومؤشرات الأداء.
- الطلبات وتفاصيل الطلب وتحديث الحالة.
- المنتجات.
- هيكلة الكتالوج: التصنيفات والعلامات والخصائص.
- المخزون.
- التقارير.
- الإدارة: الموظفون، الكوبونات، المرتجعات، والمراجعات.
- الشحن والتسويق: طرق الشحن، صفحات الهبوط، العملاء المحتملون، وقوالب التواصل.
- التجارة الاجتماعية: الاتصالات، التفاعلات، القوالب، والأتمتة.
- الذكاء الاصطناعي.
- المراقبة التشغيلية.
- المالية والمدفوعات والتسويات.
- الإعدادات.

جميع الخدمات المحلية متوقفة حاليًا، وآخر تحقق للواجهة نجح عبر:

```bash
npm run build
npm run lint
```

## 2. النواقص ذات الأولوية العالية

### أ. الطلبات والشحن

**الوضع الحالي:** عرض الطلبات، تغيير حالة الطلب، الإلغاء، عرض التفاصيل، وتعديل حالة الشحنة الموجودة.

**النواقص:**

- تشغيل تصدير الطلبات فعليًا بدل رسالة placeholder.
- عرض timeline الطلب من endpoint الحقيقي.
- إنشاء شحنة جديدة من داخل تفاصيل الطلب:
  - طريقة الشحن.
  - شركة الشحن.
  - رقم التتبع اليدوي.
  - Idempotency-Key.
- عرض الشحنات إذا لم تكن مضمّنة في response الطلب، عبر endpoint الطلب الخاص بالشحنات.
- إجراءات الطلب غير المكتملة:
  - تأكيد الطلب.
  - إضافة رسوم الشحن.
  - التواصل مع العميل.
- ربط حالة الطلب بحالة الشحنة مع تحذير واضح عند وجود تعارض.

**الأولوية:** P0.

### ب. المنتجات والكتالوج

**الوضع الحالي:** قائمة المنتجات وCRUD أساسي، مع واجهة للتصنيفات والعلامات والخصائص.

**النواقص:**

- شاشة تفاصيل المنتج.
- إدارة variants:
  - إنشاء variant.
  - تعديل وحذف variant.
  - السعر والمخزون وSKU.
- إدارة media للمنتج والـvariant:
  - رفع صورة.
  - حذف الصورة.
  - إعادة ترتيب الصور.
- استيراد المنتجات من endpoint `products/import`.
- استكمال تعديل وحذف التصنيفات والعلامات والخصائص.
- إدارة قيم الخصائص وليس اسم الخاصية فقط.
- دعم pagination والبحث من الـAPI بدل تحميل القائمة كاملة.

**الأولوية:** P0.

### ج. المخزون

**الوضع الحالي:** عرض مستويات المخزون وتعديل الكمية.

**النواقص:**

- إجراءات reserve وrelease.
- سجل حركات المخزون.
- فلترة المنتجات منخفضة المخزون.
- عرض المخزون على مستوى variants.
- سبب التعديل وملاحظته في timeline واضح.
- معالجة أخطاء تعارض المخزون برسالة مفهومة للمستخدم.

**الأولوية:** P1.

### د. المدفوعات

**الوضع الحالي:** شاشة بحث مرتبطة بالطلب وإجراءات تأكيد/استرجاع.

**النواقص:**

- عرض كل عمليات الدفع داخل تفاصيل الطلب دون إدخال رقم الطلب يدويًا فقط.
- عرض تفاصيل العملية ومزود الدفع والمرجع والمبلغ.
- تأكيد قبل refund مع إظهار المبلغ والمرجع.
- حالات الدفع والفشل وعمليات retry.
- ربط لوحة عمليات الدفع ببيانات endpoint `operations/dashboard` الفعلية.

**الأولوية:** P1.

## 3. النواقص المتوسطة في الشاشات الحالية

### أ. التجارة والتسويق

**الوضع الحالي:** طرق الشحن، صفحات الهبوط، العملاء المحتملون، قوالب التواصل، ونوافذ إحصائيات صفحات الهبوط.

**النواقص:**

- تعديل وحذف صفحات الهبوط.
- تعديل حالة العميل المحتمل عبر endpoint `landing-leads/{lead}`.
- عرض تفاصيل الإحصائيات بشكل بطاقات مسماة بدل عرض مفاتيح JSON الخام.
- اختيار نطاق زمني للتحليلات.
- نشر/إلغاء نشر مع إظهار الرابط العام للصفحة.
- تعديل وحذف طرق الشحن بدل الحذف فقط.
- إضافة رفع أو إدارة أقسام صفحة الهبوط عندما يدعمها الـAPI.

**الأولوية:** P1.

### ب. التجارة الاجتماعية

**الوضع الحالي:** الاتصالات، التفاعلات، قوالب الرسائل، وقواعد الأتمتة.

**النواقص:**

- شاشة المحادثات؛ الـAPI يدعم عرض المحادثة، الرسائل، الإرسال، pause/resume/manual.
- فتح المحادثة من التفاعل بدل الرد السريع فقط.
- تعديل الاتصال والقالب وقاعدة الأتمتة.
- معاينة قالب الرسالة عبر endpoint `templates/{id}/preview`.
- فلاتر التفاعلات حسب القناة والحالة والتاريخ.
- اقتراح رد بالذكاء الاصطناعي داخل شاشة المحادثة.
- إظهار صلاحيات المستخدم قبل عرض الأزرار الحساسة.

**الأولوية:** P1.

### ج. المراقبة التشغيلية

**الوضع الحالي:** الطلبات المتأخرة، التنبيهات، الفلترة، التأكيد والحل، وتشغيل الفحص.

**النواقص:**

- شاشة إعداد قواعد المراقبة.
- تعديل `rule_type`, `days`, `is_enabled`.
- عرض تفاصيل التنبيه.
- إجراءات bulk acknowledge وbulk resolve.
- تحديد عدة تنبيهات.
- فلترة حسب severity وprovider وdelay_type والبحث.
- pagination.

**الأولوية:** P1.

### د. المالية والتسويات

**الوضع الحالي:** قواعد الضرائب، ملخصات التسويات، وسجلات التسويات مع finalize.

**النواقص:**

- تصدير مزودي التسوية فعليًا.
- استيراد settlement file من الواجهة.
- عرض تفاصيل settlement وitems.
- إعدادات settlement import.
- فلاتر التاريخ والمزود والحالة.
- عرض ملخص التسويات كرسوم ومؤشرات واضحة بدل JSON أو جداول عامة.

**الأولوية:** P1.

### هـ. الإدارة

**الوضع الحالي:** شاشة موحدة للموظفين والكوبونات والمرتجعات والمراجعات.

**النواقص:**

- تعديل الموظف بدل الإنشاء والحذف فقط.
- حقول الموظف كاملة مع validation مطابق للـbackend.
- تعديل وحذف الكوبونات، تاريخ الصلاحية، الحد الأدنى، ونطاق المنتجات.
- دورة المرتجع الكاملة:
  - approve.
  - receive.
  - inspect.
  - reject.
- عرض سبب المرتجع والمرفقات والمبلغ.
- فلاتر المراجعات حسب الحالة والتقييم.
- moderation status واضح مع سجل الإجراء.

**الأولوية:** P1.

## 4. نواقص عامة في تجربة الاستخدام

### التنقل والصلاحيات

- استبدال `activeNav` داخل `App.tsx` بتوجيه واضح باستخدام React Router.
- حفظ الشاشة الحالية عند refresh.
- حماية الصفحات حسب الصلاحيات.
- إخفاء الأزرار التي لا يملك المستخدم صلاحيتها.
- إضافة breadcrumb للشاشات الفرعية.
- إضافة صفحة 404 وصفحة منع الوصول.

### حالة البيانات

- توحيد شكل responses التي تأتي أحيانًا كمصفوفة وأحيانًا داخل `{ data }`.
- إضافة React Query أو طبقة cache موحدة.
- إلغاء الطلبات عند مغادرة الشاشة.
- retry محدود للأخطاء المؤقتة.
- skeleton موحد لكل الجداول.
- رسائل خطأ تفصيلية حسب status code.
- معالجة انتهاء token وإعادة المستخدم إلى تسجيل الدخول.

### النماذج

- استخدام schema validation موحد.
- رسائل validation من Laravel بالعربية.
- منع double submit.
- confirmation dialogs للإلغاء والحذف والاسترجاع.
- دعم optimistic updates فقط في الإجراءات الآمنة والقابلة للعكس.

### التصميم والاستجابة

- اختبار RTL على الشاشات الصغيرة.
- تحسين القائمة الجانبية على الهاتف.
- إضافة حالات hover/focus/disabled لجميع الأزرار.
- تحسين الجداول الطويلة والـhorizontal scroll.
- توحيد modal وdrawer وtoast.
- دعم keyboard navigation وARIA labels.

## 6. خطة التنفيذ المقترحة

### المرحلة 1 — إكمال التدفقات الحرجة P0

1. استكمال الطلبات: timeline، export، confirm، shipping charge، contact.
2. إنشاء الشحنة من تفاصيل الطلب.
3. إكمال variants وmedia للمنتجات.
4. إضافة import products.
5. اختبارات smoke لتدفق login → orders → product.

### المرحلة 2 — التشغيل اليومي P1

1. reserve/release وسجل المخزون.
2. تفاصيل عمليات الدفع وrefund confirmation.
3. إدارة المرتجعات كاملة.
4. إدارة الموظفين والكوبونات بالكامل.
5. إعدادات المراقبة والتنبيهات الجماعية.
6. تفاصيل واستيراد وتصدير التسويات.

### المرحلة 3 — التسويق والتواصل P1

1. محادثات التجارة الاجتماعية.
2. تعديل ومعاينة قوالب الرسائل.
3. تعديل العملاء المحتملين.
4. إكمال CRUD صفحات الهبوط.
5. تحسين تحليلات صفحات الهبوط برسوم وفلاتر زمنية.

### المرحلة 4 — الصلاحيات والجودة P0/P1

1. permission-aware navigation.
2. توحيد إدارة البيانات والأخطاء.
3. فصل App وAPI إلى modules.
4. اختبارات المكونات والتدفقات الأساسية.
5. مراجعة responsive/accessibility.

### المرحلة 5 — التحسينات الاختيارية P2

1. رسوم بيانية متقدمة للتقارير.
2. bulk actions عامة في الجداول.
3. export موحد لكل التقارير.
4. إشعارات realtime عند وصول طلب أو تنبيه.
5. audit log للعمليات الحساسة.
6. dark mode إذا كان مطلوبًا في التصميم النهائي.

## 7. ترتيب التنفيذ المقترح للخطوة التالية

الخطوة التالية الأفضل هي **إكمال الطلبات والشحن** لأنها أكثر وحدة حساسية للتشغيل اليومي، وبالترتيب التالي:

1. order timeline.
2. إنشاء shipment.
3. تحديث حالة shipment.
4. تصدير الطلبات CSV.
5. confirm/cancel/contact/shipping-charge.
6. اختبار التدفق كاملًا على API محلي.

بعدها ننتقل إلى **variants وmedia للمنتجات** ثم **التسويات والمرتجعات**.
